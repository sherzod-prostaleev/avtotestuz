# M2-03 Click Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use `- [ ]`. Tasks 2 and 3 are independent (disjoint files, no shared state) and MAY be dispatched in parallel via isolated worktrees; all other tasks are sequential.

**Goal:** Click Merchant Shop API (Prepare/Complete) webhook + provider-generalized checkout-initiate, so a user can pay via Click and get a VIP entitlement, in sandbox mode — the second payment provider alongside Payme (M2-02).

**Architecture:** Same `payment` row/state-machine as Payme. A new `click_transaction` table (we mint the id, Click echoes it back as `merchant_prepare_id`) tracks Click's own two-phase Prepare/Complete flow. Public `POST /billing/click` webhook authenticates itself via an MD5 `sign_string` (no separate Basic-Auth layer, unlike Payme). `Service.StartCheckout` is generalized to build either provider's checkout URL. Complete grants VIP via `billing.Service.GrantDays`, wrapped in a DB transaction with row-locking from Task 5 onward — Payme's M2-02 postmortem found this exact atomicity/locking gap late and had to patch it after merge; here it is designed in from the start.

**Tech Stack:** Go, chi, pgx, sqlc. Amounts: so'm (bigint) both in `payment.amount_uzs` and Click's wire format — **no tiyin conversion**, unlike Payme. Tests: `testdb`, `-p 1`.

## Global Constraints
- `PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` for go; sqlc at `~/go/bin`; `make generate` for sqlc (run from repo root `/home/sher/Рабочий стол/avtotest`).
- Webhook ALWAYS returns HTTP 200 for any request that reaches signature verification or later; a non-POST method may respond with a plain HTTP 405 (Click's protocol has no JSON envelope for pure transport-method errors, unlike Payme's -32300).
- Response body is **flat JSON** (`{click_trans_id, merchant_trans_id, merchant_prepare_id|merchant_confirm_id, error, error_note}`) — no JSON-RPC envelope.
- Sign formula (exact, order matters): `MD5(click_trans_id + service_id + secret_key + merchant_trans_id + (action=="1" ? merchant_prepare_id : "") + amount + action + sign_time)`, compared case-insensitively-hex via constant-time compare. Empty `secret_key` ⇒ never matches ⇒ always `-1`.
- Error codes (exact, do not invent others): `0` success, `-1` sign check failed, `-2` incorrect amount, `-3` action not found, `-4` already paid, `-5` account (`merchant_trans_id`) not found, `-6` transaction (`merchant_prepare_id`) not found, `-8` bad/malformed request or unexpected internal failure, `-9` transaction cancelled.
- Amount comparison: `Amount` arrives as a decimal string; parse with `strconv.ParseFloat`; mismatch if `math.Abs(parsed - float64(amount_uzs)) > 0.01`.
- `click_transaction.state`: `0` waiting (post-Prepare), `1` confirmed (post-Complete success), `-1` rejected. No further states.
- DB test convention: `testdb.New(t)` migrates + truncates; DB tests insert their own `profile`/`tariff`/`payment` fixtures. `pool.Exec` does not support multiple SQL statements in one call.

  ```go
  package click

  import (
      "crypto/md5"
      "crypto/subtle"
      "encoding/hex"
  )

  func computeSign(req clickRequest, serviceID, secretKey string) string {
      s := req.ClickTransID + serviceID + secretKey + req.MerchantTransID
      if req.Action == "1" {
          s += req.MerchantPrepareID
      }
      s += req.Amount + req.Action + req.SignTime
      sum := md5.Sum([]byte(s))
      return hex.EncodeToString(sum[:])
  }

  func validSign(req clickRequest, serviceID, secretKey string) bool {
      if secretKey == "" {
          return false
      }
      want := computeSign(req, serviceID, secretKey)
      return subtle.ConstantTimeCompare([]byte(want), []byte(req.SignString)) == 1
  }
  ```
